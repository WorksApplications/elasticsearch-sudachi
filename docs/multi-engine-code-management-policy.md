# 検索エンジン (ES/OS) の API 差分対応のためのコード管理ポリシー

## 概要

Elasticsearch / OpenSearch やそのバージョンによって API が異なるため、それぞれに対応するコード差分を扱う必要がある。
本リポジトリではこの差分ごとにブランチを分割して管理する。

本ドキュメントでは、このブランチの管理に関するポリシーを定義する。

## 基本方針

- 共通機能はデフォルトブランチが責務を持つものとし、ブランチによる分岐は最小に保つ.
- API の異なる系列（engine + major version）ごとに 1 ブランチを持つことを基本とする
  - 系列内での API 差分が発生した場合はさらにブランチを分割することも許す
- 変更の起点はデフォルトブランチとし、必要な系列へ cherry-pick/backport する

## コード管理ポリシー

### 現行ブランチ

- `develop`: 共通機能ブランチ（デフォルト）

さらに対応する検索エンジンおよびそのメジャーバージョン毎にブランチを持つ

- `es-9`: Elasticsearch v9.\* 以降（v3.4.0 では未対応）
- `es-8.10+`: Elasticsearch v8.10.\* 以降
- `os-3`: OpenSearch v3.\* 以降
- `os-2.6+`: OpenSearch v2.6.\* 以降

注記:

- 各ブランチの対応対象とするバージョンは `README.md` と CI マトリクスで明示するものとする
- サポート終了後も該当ブランチは維持する
  - 履歴保持のための維持であり、リリースや更新は対象外とする
  - セキュリティ修正やビルド可能性の維持といった対応も明には行わない

### ext ディレクトリによるコード分岐の扱い

- 新規のバージョン差分は `src/main/ext` へ追加せず、対象系列ブランチに直接実装する
- `src/main/ext/` および `src/test/ext/` の使用は段階的に縮小する
  - `src/test/ext/` については同系列内でのテストのみでの差分を吸収するために使用することを許す

### minor 差分対応のためのブランチ分割

同系列（engine + major version）内の minor バージョン間でさらにコード差分が必要になった場合は、ブランチを分割することを許す。

分割判断は以下を目安とする。

- `src/main/` 内で minor バージョンによる大きなコード差分が発生した
  - ただし `src/test` 内差分は対象外とし、`src/test/ext` を使用するものとする

ブランチ分割時チェックリスト：

- [ ] ブランチを分割する
  - 新規ブランチ名は `[engine]-[min major.minor]-[max major.minor]` とする
  - 分割前ブランチは `[engine]-[major.minor]+` にリネームする
  - e.g. `es-9` から `9.2` 以前を分割する： `es-9.0-9.2`, `es-9.3+`
  - e.g. `es-8.14+` から `8.15` 以前を分割する： `es-8.14-8.15`, `es-8.16+`
- [ ] ドキュメントを更新する
  - 各ブランチがサポートするバージョンを明記する (`README.md`)
  - 分割の理由を明記する (`README.md`)
- [ ] github workflow を更新する
  - test workflow：分割後ブランチがそれぞれのサポート対象バージョンを受け持つ
  - release workflow：分割後ブランチがそれぞれのサポート対象バージョンを受け持つ
  - backport workflow：バックポート先ブランチを分割後に更新する
    - PR ラベルを更新・追加する
- [ ] 既存の issue/PR を確認する
  - ベースブランチの更新
  - backport ラベルの付け替え
  - 分割による影響への対応

## PR 運用ポリシー

### ベースブランチ

- 複数系列に共通する変更は `develop` をベースに PR を作成する
  - 変更は cherrypick/backport ルールに従って必要系列へ展開する
  - 例：フィルタなど共通ロジック・そのテスト、ドキュメント、ビルド設定
- 特定系列に固有の変更は対象系列ブランチをベースに PR を作成する
  - 例：固有のバグ修正、依存関係更新
- 特定検索エンジンや major バージョン内で共通する変更は、それらのうち最新のブランチをベースに PR を作成する
  - 変更は cherrypick/backport ルールに従って必要系列へ展開する
  - ただしその差分がバックポート可能でないと想定される場合は個別に PR を作成する
  - 例：Elasticsearch に関するバグ修正

確認のため、PR 内容にも当該のブランチおよびバックポート要否・対象を明記すること

#### ベース選択目安

`search/` および関連テストへの更新は該当するブランチ、それ以外（`spi/`, `lucene/`, `build.gradle` など）への更新は `develop` をベースにすることが基本となる。

- gradle、CI、ビルド設定などの更新： `develop`
- フィルタの新規追加・修正： `develop`
- 特定バージョンに固有のバグ修正：当該バージョンを含むブランチ
- 特定検索エンジンに固有のバグ修正：当該検索エンジンの最新ブランチをターゲットとし、バックポート

### cherrypick / backport ルール

cherrypick/backport の要否と対象ブランチの確認は PR 単位で行う
該当する元 PR にラベル `backport [target branch]` を付与する

- e.g. `backport es-9`
- 当該 PR のマージ時（マージ済みならラベル付与時）にバックポートアクションが実行されるので、これのマージをもって完了とする
  - 自動作成 PR がテストに失敗した場合は適宜修正を行う

## CI / テスト運用

- 系列ブランチごとにサポート対象バージョンに対するテストを持つ
  - major.minor 単位とし、patch バージョンは最新のみカバーする
  - このテストがパスすることをもって当該バージョンをサポートしたものとみなす
- テストにおける系列内差分は `src/test/ext/` で管理する（テスト用途に限定）
  - `src/test/ext/` へのコード追加時は、対象バージョン範囲をコードコメント等に明記する

## リリース運用

- リリースは、 `develop` の開発状況や重大なバグの修正、新規バージョンのサポート追加などを目安に行う
  - 各リリースでは、変更が一部系列のみにしかない場合でも、すべてのサポート系列のビルドをリリースする
  - 新規サポートの追加のみで、機能変更がない場合は、既存の最新リリースを拡張する形でリリースを行う場合がある
- 各ブランチのリリース対象となるコミットに付与した git タグをリリース対象とする
  - タグは `[version]-[engine]-[engine major version]` のようにリリースバージョンに加え系列を識別可能にする
    - 例: `v3.5.0-es-8`, `v3.5.0-es-8.10-8.13`, `v3.5.0-os-3.2+`
- 各ブランチからそれがサポートする各バージョンのビルドを作成し、github release にアセットとして公開する

## 変更履歴および経緯

### 2026-03 - now: ブランチ単位での差分管理

現行の管理方式

- ポリシー変更理由:
  - バージョン固有差分をブランチ境界に寄せ、ブランチ内のコードを単純化するため
  - コード変更の対象系列を明確化し、開発やレビューを容易にするため
- 受容する欠点:
  - ブランチ数増加に伴う同期・backport・リリース判断コストの増加
  - CI 設定やテストマトリクスの管理対象増加

### - 2026-03: `ext/` ディレクトリによる差分保持

- `src/main/ext/` と `src/test/ext/` に差分コードを分離し、`BuildSrc/` で独自に定義した `es.sources` gradle プラグインで切り替えを行っていた
  - これにより単ブランチでのコード管理を実現していた
- この方式の欠点:
  - `ext` と本体の責務分散
  - 差分の追跡性低下
  - 新バージョン対応時の変更範囲拡大
